# 跟着一篇帖子读懂小红书运营 Agent

面向第一次接触 Agent 开发、希望能独立讲解和维护这个项目的同学。本文按 2026-11-18 在 Windows 项目中读到的源码编写。下方场景是教学示例，不是线上运行记录。第一次阅读先掌握第 1～4 节，再开编辑器。

## 1. 一张图：谁在做事，谁在做决定？

假设你在飞书发：“选题：Claude 的记忆研究，讲清楚它和聊天记录有什么不同。”你的目标是一篇可以发布的图文，不是依次执行十条命令。系统怎么把一句话变成作品？

~~~text
你在飞书给选题 ─→ 飞书网关 ─┐
定时发现热点 ──────────────┴→ 记录选题与待办 → Worker 取任务
                                                  ↓
                                           创作 Agent
                              搜资料 ↔ 阅读 ↔ 写稿/改稿 ↔ 渲染/审阅
                                                  ↓
                                       飞书展示具体版本给你
                                   ┌──── 修改意见  → 创作新版本
                                   └──── 批准该版  → 发布入口
                                                       ↓
                              新版发布 Agent（开关控制）→ 发布前校验
                                                       ↓
                                           HTTP → 小红书桥接程序
                                                       ↓
                                     核对平台结果 → 飞书回执
~~~

SQLite 贯穿整张图：它保存待办、创作版本、审批、发送记录和通知。图中两个 Agent 是两个**职责和权限不同的程序循环**，不意味着要部署两个模型。创作阶段能改稿但不能自行发布；发布阶段可以处理已经批准的稿子，却不能擅自把它改成另一篇。旧发布路径也还存在，因此看到项目能发帖，不等于新版发布循环已在线启用。

## 2. 技术栈为什么这样选？

- **Python 3.12** 运行后台程序。飞书网关接收事件，Worker 执行耗时任务。本机控制台和命令行供维护者使用。它们是不同入口，不需要你在手机上一直开着聊天。
- **DeepSeek API** 负责语言判断和生成，例如选下一步工具、撰写正文、理解修改意见。**DeepSeek Harness（DSH）** 是开发时用来修改和测试项目的助手，不是每条飞书消息都要经过的运行服务。产品里的模型调用看 [llm.py](../bot/adapters/llm.py)，不是看 DSH 的开发提示词。
- **SQLite + 本地文件** 分别保存业务记录和图片等文件。数据库里能记录“批准的是哪一版、对应哪些图片”；只保留图片文件本身回答不了这个问题。SQLite 也承担本机任务队列，因此理解这个版本不必先学 Redis 或消息中间件。
- **飞书 SDK（lark-oapi）** 支持机器人长连接；**Pillow** 把内容和视觉方案渲染成图片。注意“AI 参与图文创作”并不意味着每张图都是扩散模型生成的。看 [渲染入口](../bot/services/creator_agent/live.py) 比猜图片来源可靠。
- **小红书桥接程序** 负责与平台交互。项目虽然使用名为 xiaohongshu-mcp 的社区桥接，但应用通过自己的 HTTP 适配器使用所需能力，并未把桥接的整套工具开放给模型。桥接程序、应用的发布工具、DeepSeek 模型是三样东西。

## 3. 跟读：从选题到一篇获批图文

**第一站：接单。** [飞书网关](../bot/lark_gateway.py) 收到消息，把业务处理交给[入站处理](../bot/services/approvals.py)等模块。创作入口将指令整理成 brief，即“这篇为谁写、想表达什么、有哪些要求”，并记录待办。飞书重复投递同一条消息不等于你下了两次订单；系统用消息标识识别重复。定时发现热点也能启动创作，但它没有一条来自你的原始飞书消息，入口和去重依据不完全一样。

**第二站：让模型选动作。** 打开 [创作 runner](../bot/services/creator_agent/runner.py)，找 AgentRunner 和 complete_json。每轮把目标、已有材料、当前稿件和可用工具告诉模型。模型提出结构化动作，例如 read_source 加一个来源标识；Python 检查动作和参数，运行工具，再把结果交给下一轮。这里的 ReAct 指“根据观察选择行动，再读取行动结果”，不需要程序拿到或展示模型的私有思维过程。

以本例来说：如果只有媒体标题，下一步可能是查找并阅读原文；如果已拿到原文但有一句话夸大了结论，下一步可能是改那句话，而非重复全网搜索。这是 Agent 和固定脚本的关键区别。另一方面，模型不能因为“我觉得差不多了”就跳过批准。步数、预算、无进展退出和允许的动作由程序约束。

**第三站：工具真正干活。** 在 [tools.py](../bot/services/creator_agent/tools.py) 看模型可选的动作，到 [live.py](../bot/services/creator_agent/live.py) 看真实执行。按用途记就够了：

- 发现和取材：discover_topics、search、read_source、inspect_claims、recall_context。搜索给出候选；阅读正文和核对声明回答“这句话凭什么写”。信息聚合站能提供线索，不天然等于原始证据。
- 创作与修改：draft_artifact、revise_artifact。artifact 是内部作品版本，不是已发布帖子。比如你说“少谈产品宣传，改用一个记忆失败的例子”，程序应让模型结合原稿和意见产生新版，再送给你看。
- 图文检查：render_images、inspect_layout、review_artifact。排版能否放得下，用程序检查；观点是否跑题，可以由模型参与审稿。[review_artifact](../bot/services/creator_agent/live.py) 同时能看到模型审稿与规则处理，不能简单理解成“全部由模型打分”。
- 交接：submit_for_approval、ask_owner。前者是交付给你审批，不等于发布；后者是需要人补充信息时的工具，不能据此推断飞书里任意自然语言都能正确执行。

**第四站：批准的是版本，不只是选题。** 同一个选题可以有多版正文和图片。审批把同意绑定到具体版本及内容指纹（hash，文件字节变化时指纹通常也会变）。这样你批准第 2 版，后台就不能误取第 3 版发布。作品符合你的意图，最终由你决定。

## 4. 发布是另一个问题：怎么知道真的发成了？

创作 Agent 关心“还需要补什么”；发布 Agent 关心“我被允许发送什么，平台实际发生了什么”。从 [发布 runner](../bot/services/publication_agent/runner.py) 看模型可以选择的动作；从 [发布服务](../bot/services/publish.py) 看提交前的检查；从 [平台适配器](../bot/adapters/publishers.py) 看真正的 HTTP 调用。模型说“成功”不是回执。

想象三种情形，理解它们比记住所有状态名更重要：

1. **提交前缺图。** 若有批准时的同字节备份，可恢复、核验，再尝试发布。这叫修复；现场生成一张相似的图不是修复，因为你没批准过它。
2. **需要重新登录。** Agent 可以检查并通知你扫码。你回复已登录后，程序还要核对目标账号。模型不能代替你证明账号所有权。
3. **提交后超时。** 请求可能已经生效；这不是“已失败”，而是 unknown。再点一次可能发出两篇。正确动作是查询原发送记录，结合目标账号、发前列表基线、平台的笔记标识等证据判断；查不到时不把猜测写成成功。

**为什么需要程序规则？** 选题和表达没有唯一答案，适合交给模型。是否重复提交、是否批准过当前版本、回执属于哪个账号，是必须一致的事实，不能让模型凭语气决定。持久化的自动对账可以由普通程序运行，不需要为了体现“智能”而反复付费问模型。

## 5. 持久化：电脑重启后，它靠什么接着干？

不是靠模型记住昨天的对话。你可以把数据库理解成几本账：

- **jobs：接下来要做什么。** Worker 周期性取到期待办。任务记录在磁盘上，和“某次 Python 函数还在执行”是两回事。
- **创作 run、steps、artifacts：为什么走到这一版。** run 对应一次创作任务；step 是一次动作及观察；artifact 是某版作品。检查点保存可恢复的进度。入口见 [创作 store](../bot/services/creator_agent/store.py)。
- **drafts、approvals：用户实际看过什么、同意了什么。** 内部写过稿不代表已经送审，送审不代表已经批准。
- **publication_tasks、publish_attempts：业务目标和发送尝试。** “把这篇发出去”是一项任务；某次向平台提交是一次尝试。查询第一次尝试的结果不应该产生第二次提交。
- **通知记录：该告诉用户什么。** 平台成功落库与飞书送达是两件事。通知失败时应补通知，不应重新发帖。

这解释了两个常见术语：**幂等**指同一消息重复处理不会多产生一篇帖子；**对账**指本地记录不确定时，读取平台证据核实结果。它们是设计目标，不能仅凭用了 SQLite 就宣称所有故障都已解决。

## 6. 上手路线：不发帖也能学会追代码

1. **先追入口。** 打开 [Worker](../bot/worker.py)，搜 def tick，再看它如何分派任务。练习：解释为什么收到飞书消息与写完帖子不必发生在同一个函数里。
2. **只追一个工具。** 在创作 tools 里搜 revise_artifact，沿着 live 实现读到新版产物，再回 runner 看下一轮能观察到什么。练习：画出“用户给意见”和“模型自己审稿提出意见”分别从哪里来，最后在哪里改作品。
3. **追一次超时。** 打开 [离线演示](../tests/test_publication_round2_demo.py)，搜 without_owner_message。不要先读整份模拟代码；先找四件事：平台何时报超时、后来什么时候出现笔记、Worker 何时重启、最后断言发过几次。
4. **对照正反例。** 在同一文件找 cross_account 和 same_account。两种情况下标题都可以相同，为什么结果应该不同？能指出哪一层提供账号证据，就已经读懂发布适配器的价值。

在已装好依赖的 Windows 项目目录里，可以只运行交付用的离线演示：在 PowerShell 执行 `.\.venv\Scripts\python.exe -B -m unittest tests.test_publication_round2_demo`。这组测试使用模拟桥接和通知器，不需要配置你的真实账号。课堂上展示测试要称作模拟，不说成平台真机验收。

## 7. 如何准确介绍当前版本

用户此前报告旧路径已真实发帖。新版的错账号拒认、主人触发后的延迟对账、登录及图片恢复等已有离线演示。**本次阅读源码时**，[首次 unknown 的处理](../bot/services/publication_agent/live.py) 已出现自动排入对账的实现，测试文件也已有“无主人消息、重启后恢复”的用例；因此旧笔记中“首次必须由主人触发”不能当作最新源码描述。本文编写时没有重新执行测试，也没有检查生产开关或真机收件，不能据此声称最新改动已上线。

课程答辩可以这样开头：“我做的是一个有人工审批的内容运营 Agent。创作阶段由模型根据已有材料和反馈选择工具、迭代图文；审批以后，发布阶段只处理获批版本，并从平台证据判断结果。SQLite 记录每一步，让系统可以跨消息和重启工作。”然后展示一次模型选择工具、一次用户修改意见、一次超时不重复发布。这样老师看到的是三个可验证的设计，而不仅是一张架构图。这个项目属于大模型应用与智能体工程，不要把使用 DeepSeek API 描述成自己训练或微调了模型。
