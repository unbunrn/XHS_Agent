## ② 主人真正想要的使用体验

主人在飞书里看到一张能读懂来源、图片顺序、风险和下一步的审批卡；批准哪一版，就只发哪一版。发送失败或结果未知时，系统用中文说明“发生了什么、已经查了什么、主人下一步做什么”，支持查原因、恢复资产、重新登录、取消和显式确认未发布；**不重复发、不静默成功、不要求主人理解内部状态机**。发布命令使用 XH-… 审批码，自然语言无编号定位尚未完成。

## ③ 三个最重要的设计决定

1. **只发布批准版本。** 审批绑定平台、账号、草稿版本、正文 hash、图片 hash、顺序、时间和有效期；任何修改都会使旧审批失效。原因是发布后无法撤回“发错版本”，必须在发送前把可审计对象冻结。
2. **unknown 只对账，不重发。** 请求可能已到平台但回执丢失；再 POST 会制造重复笔记。因此保存发送前账号/feed 基线，只有“已验证账号 + 同账号、基线外唯一新增、可归因笔记”或受信回执才能确认原 attempt；先核对一次；查不到则保持 unknown，再按 30、60、120 秒最多安排三次延迟核对，仍无结果才停下等主人。自动与手动“修复”共用同一条对账链，只有“确认未发布并重试”能授权新提交。
3. **不再新增 Agent。** V2 负责创作与审批，`publication_agent` 负责任务、恢复和对账，边界已经够用。新增 Agent/服务/发布状态只会增加恢复分支和重复发送风险；本轮只修首次 unknown 的触发、startup 恢复和已有对账入口。

## ⑥ 新会话的第一项工作：单篇灰度只读预检

直接检查现场并给出结论，不需要重述项目架构。核对当前 Git 版本、运行的 worker / 飞书网关、实际配置与发布开关；以只读方式查询 live DB 的 schema 版本、待处理审批、待执行的发布任务及结果未明的发送记录。不要初始化数据库，避免检查时触发迁移；不要输出凭据或原始消息。

**先回答“为什么只影响一篇”。** 发布入口使用配置开关，不能假设它按审批码隔离。结合定时运营、飞书批准入口、已有队列和在途请求，说明如何保证仅一篇新批准的作品走新版，不重放历史稿；写清哪些服务需要临时暂停、预计影响，以及结束后如何恢复。若不能隔离，指出具体阻塞，不开启开关，不为预检开发新模块。

**预检交付即停。** 给主人四项结果：现场状态、可以或不能单篇灰度及依据、备份与退出步骤、需要主人决定的事项。此阶段不改代码或配置、不停服务、不迁移、不重跑全量、不发送消息或帖子。

**后续维护窗口（不属于预检）：** 主人确认范围后，按回滚文档备份、校验并做必要迁移。使用一篇在飞书新批准的稿件，核对批准版本、目标账号、发送记录、平台笔记 ID 和手机回执。扫码或平台结果需人工核实时再请主人操作。成功后恢复临时改动，不自动扩大范围；若结果未知，先对账，不重复发帖。重复事件、故障注入、回滚验证留在测试环境或副本，不拿真实账号重演。不得用旧库覆盖灰度期间新增的发送事实。
