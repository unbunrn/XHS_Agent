# 后续开发说明书

更新：2026-11-10（北京时间）。项目：`D:\Dev\Projects\bot`。本文件是后续开发入口，不代表其中规划已实现。用户的新指令优先；实际代码、有效配置和验证结果优先于过期历史说明。

## 1. 产品目标与边界

做一个可通过飞书指挥、能持续经营小红书账号的运营 Agent：搜集信息、判断选题价值、核实事实、自主决定表达形式、写稿配图、响应修改、请求审批、发布并反馈结果，逐步基于真实效果改进。

不要将目标降级为新闻搬运、固定模板填空或正文转图片。也不要把“运营者自主性”等同于绕过本人审批、随意花费或自动对外互动。账号定位暂为给中文普通用户和独立开发者讲明白 AI 工具与研究。

本轮用户仅要求提供开发文档。收到本文不等于获得真实发帖、发送测试消息、改变预算、升级容器或修改系统启动设置的授权。DSH 默认只做离线开发；实际部署与外部动作按照用户当次任务授权执行，已有明确授权不重复索取。

## 2. 已实现与已验证

- Python 3.12 本地服务：worker、Feishu gateway、本机 console；SQLite 保存任务、来源、证据、稿件、审批、预算和发布尝试。
- DeepSeek 搜索/正文获取与写作；支持自动采集和飞书手动选题。官方来源允许列表、事实与数字检查、费用记账已存在。
- 飞书本人私聊可发选题、修改、批准、拒绝及状态等命令；图片和正文会发回审批。
- 新内容有独立 caption、editorial_plan、storyboard；模型选择图文主次和页数，支持本地文字/几何布局。旧稿保持兼容。
- 改稿包含确定性差异检查与一次有预算限制的语义审核；旧审批失效、新版本重新审批。不能据此声称任何意见均能正确理解。
- Docker 小红书桥接已登录并支持真实发布。已有一篇真实笔记，发布记录保存真实ID/URL；成功确认曾依赖用户提供分享链接后人工对账。
- 来源同步误停用人工来源、60秒发布超时、确认未发布后错误占用每日额度等问题已修正。
- 2026-11-10：人工与自动额度拆分，22项相关回归测试通过。此前交接记录记载166项全套测试通过，但这不是最新额度改动后的全套结果；不要拼接成虚构的最新全测结果。

有效运行配置快照（部署前重新读取）：
- `config/bot.live.toml`：自动发布最多1条/日，人工选题发布最多5条/日；人工首次写稿最多5篇/日。按Asia/Shanghai日界计数，改稿不重复占人工选题名额。
- 待审批同时最多3篇；人工请求入口默认5次/日。每天最多5条不等于5条能同时等待审批。
- 估算费用5美元/日，模型/搜索最多200次/日；不是保证消费额或供应商硬账单限制。
- 逐篇批准仍必要，定时自动运营不意味着无审批发布。
- 发布等待360秒、HTTP发布自动重试0。结果unknown绝不能自动重发。
- 当前真实发布使用四道开关；环境变量由启动进程继承，并未全局持久化。

## 3. 当前限制

发布接口可能报告完成但没有可靠笔记ID；发布结果对账、失败通知仍不完善。没有完整开机启动/崩溃恢复方案；电脑休眠会中断服务。没有真实平台指标采集、评论/私信运营。图片视觉能力有限；diagram只是受限布局，不是任意关系图引擎。部分改稿意图仍靠关键词辅助判断。长期偏好主要是本地TOML，尚无完整的飞书偏好管理。跨平台未实现。

后续不得以单次FakeLLM测试证明真实编辑能力，也不得以HTTP200、点击按钮或任务done证明笔记已发布。

## 4. 目录与模块职责

```text
bot/
  adapters/       外部系统适配：DeepSeek、来源、飞书、小红书；协议和传输细节
  services/       研究、选题、稿件、审批、通知、发布、分析等业务流程
  web/            本机控制台静态资源
  worker.py       编排任务；不要继续堆积各服务业务细节
  lark_gateway.py 飞书接收；尽快入队，不在事件回调中长时间调用模型
  content.py      稿件数据模型、校验和正文构造
  editorial.py    编辑偏好、改稿意图及验收
  render.py       独立图片方案的本地渲染
  db.py/schema.py SQLite访问与追加式迁移
  jobs.py         持久任务、租约、恢复
  budget.py       预算预约、结算、暂停
  security.py     URL与网络访问边界
  config.py       配置默认值、读取与验证
config/           配置示例、非秘密编辑偏好、机器本地配置与秘密文件
scripts/          安装、启动、停止、健康检查、备份及专项运维入口
fixtures/         无秘密的离线数据样本
tests/            unittest测试；与业务模块对应命名
var/              本机运行数据、数据库、会话、日志、图片、测试产物；不提交
docs/             产品说明、架构、操作、阶段交付记录
```

目录维护规则：
1. 优先沿用上述结构，不另起一套agent/server/backend平行架构，不为本项目引入第二套任务队列或数据库。
2. 一个模块只承担明确职责。确需拆大文件时先保持外部接口，单独完成重构验证，不与重大功能变更混在一起。
3. 根目录只留入口、依赖及顶层说明。新工具放scripts，计划/报告放docs，临时文件与日志放var；绝不放到`D:\CodexSync\work`，那里只管理交接文档。
4. 不删除或移动现有`.venv*`、`pip-*`、var或历史文档。先列出归属、引用和是否正在使用；历史环境/缓存清理另开可审阅清单，不能顺手递归删除。
5. 代码仅在本项目修改。不要改DSH安装目录、桌面凭据、全局Python、系统执行策略或安全软件。
6. SQL变更通过schema.py追加版本，不能重写已执行迁移；同时验证旧库升级、重复初始化和记录保留。
7. 不把运行数据、Token、Cookie、私钥、原始日志或个人标识写到文档与fixtures。不要输出secrets.toml或完整Docker环境。
8. 当前目录未观察到.git。不要假定有Git回滚；写重要文件前做范围明确的本地备份。Git初始化/提交/推送不是开发任务的默认附带动作。
9. 未来建立Git时检查.gitignore：`config/bot.live.toml`也属于本机配置，当前规则未明确排除它；应使用脱敏example，审查后再纳入版本管理。不得提交真实账号与机器配置。

## 5. 开发阶段：每次只做一个

### P0：发布结果闭环（最高优先级）

目标：用户不必再问“到底发了没有”。优先读services/publish.py、notifications.py、worker.py、adapters/publishers.py和相关测试。

任务：
- 为发布成功、确定失败、前置阻塞和结果不明产生清晰、持久、幂等的飞书结果通知。通知展示稿件/审批码、当前状态、下一步；失败原因脱敏且有中文解释。
- 区分任务已消费与业务已成功；不能让done掩盖blocked。保留业务结果供状态查询，不要只留在日志。
- 构建只读发布对账：可信平台回执优先；缺少ID时查本人笔记，并结合发布时间、标题、正文或其它可得特征核对。仅同标题、空主页、没有搜到都不足以证明成功/失败。
- 对账有次数、时限和间隔；遇到延迟、多个匹配或登录失效时保持unknown并提示人工处理。不得尝试“再发一次看看”。
- 不确定结果和普通失败继续占名额；只有明确对账为未发布才释放。每天自动1/人工5仍各自独立。
- 保留原请求、尝试记录与失败证据。已批准稿件内容变化必须重新审批。

验收：离线覆盖带ID成功、无ID但唯一可信匹配、同标题冲突、平台延迟、断线、通知重放、重启、重复回调；每个审批最多一次提交。先用录制的脱敏响应验收，不调用真实发帖。交付时明确下一次真实验收还需要什么。

### P1：长期运行与恢复

任务：选择最小Windows运行方案；复用现有start/stop/process_identity，不引入庞大守护框架。启动前检查配置、重复实例、端口、Docker健康、身份与开关。进程异常退出可受控恢复；失败退避、限制重启频率。网络恢复后恢复接收；数据库租约与unknown发布按原规则处理。

启动服务的健康不等于登录有效或可以发布。不要自动重置Cookie、放宽防火墙或关闭杀毒。系统启动注册和服务启用是部署动作，先提供可审阅安装/卸载方案与离线验证，再按用户授权应用。

验收：worker/gateway分别退出、网络断开恢复、重复启动、过期PID、Docker未运行；均不重复发稿/通知。提供明确停止、卸载、回滚说明。不能把“可启动”写成已验证24小时无人值守。

### P2：飞书任务控制

任务：提供清晰的任务列表/单篇进度/排队原因；取消未执行任务、修改优先级；持久区分临时修改与长期偏好。长期偏好先明确解释拟保存内容，可通过命令确认、查看与撤销。自然语言含糊时允许澄清，但不要每次都问模板问题。不得把网页文本变成主人指令。

验收：本人p2p检查、重复消息幂等、过期审批、取消与worker并发、已经提交的发布无法假装撤回。所有指令走统一业务服务与审计，console和飞书不能有两套互相矛盾规则。

### P3：运营反馈

先接入真实可读指标，保存抓取时间、来源、缺失与不确定性。不可读就明确missing，不能写0替代未知。先做简单周期复盘：同类选题比较、表现与可能解释、下一次实验建议。不要用极少样本断言算法偏好或因果。不要据此自动扩大预算、提高发帖频率或擅自评论私信。

### P4：编辑自主性与视觉质量

当前用户明确同意成熟运营者能力后续再提升；不要抢在P0/P1之前做大规模美化。
- 按内容/受众选择形式：一张图或多张图、观点/拆解/对比/关系图等，不固定四段、卡片数、图文字数比例。
- 标题和关键词合理呼应不等于重复；检查图文是否互补，不追求机械零重合。
- 改稿以原话、旧正文与旧图片方案为上下文；语义理解应逐步替代脆弱的关键词硬判定。
- 引入素材/图像服务前先确认可用API、成本与授权；只有DeepSeek文本API时，不声称已支持生成插画。
- 实际检查PNG的字号、换行、留白、可读性、事实表达。几何箭头不能暗示来源不存在的先后或因果。

验收：选择不同内容的固定评估集，检查不同策略是否合理，而不是强行让每篇外观不同；包含模糊修改、保留部分、只改图、二选一意见等。真实模型评估须限量并记账。

## 6. 开发与部署纪律

- 每阶段先列受影响模块、要解决的故障/需求和验收点，简短即可。不要全文阅读全部历史记录。
- 默认用FakeLLM、mock publisher、测试notifier和var/tests临时库。严禁为跑测试修改var/live数据库或读取生产秘密。
- 不新建无必要依赖，不升级已固定Docker镜像。XHS v2.7.2的compose及启动器有摘要绑定，任意改compose会破坏启动验证。
- 修改完成先跑最小相关测试；通过后只在涉及范围较大时跑一次全套。没有新变更或未解问题就不要重复测试、反复自审或继续规划。
- 服务代码改动不会自动进入现有Python进程。开发结果与部署结果分别记录。部署先查看在途任务，避免中断publishing；备份SQLite用Database.backup_to，不复制运行中WAL的单个主文件冒充完整备份。
- 发布开关包括live配置与BOT_ALLOW_REAL_PUBLISH；不能在测试终端默认打开。不要擅自全局保存该变量。
- 真实消息、真实模型调用和真实发布分别注明授权及验证范围。若用户只要求开发，停在离线可验收结果；不要顺便发“测试帖”。
- 未知错误保留现场与审计；不删除失败记录、不重置计数、不调整审批状态来强行通过检查。

常用离线验证（在项目根目录）：

```powershell
& .\.venv\Scripts\python.exe -m unittest tests.test_approval_publish -q
# 按改动挑选相关模块，不要求每次执行以下全套
& .\.venv\Scripts\python.exe -m unittest discover -s tests -q
```

## 7. 每阶段交付格式与文档维护

完成一阶段，更新本文件相应状态，并在`docs/delivery/`写一份简短报告，例如`P0-publication-feedback-20261110.md`；该目录仅在首次真实交付时创建，不预制空报告。

报告必须包含：解决的问题；变更文件；行为变化；实际测试命令/结果；是否部署；是否调用真实服务；仍存在的限制；数据库迁移/回滚方式；下一步。失败或未执行明确写出来。时间用北京时间+08:00，文档更新时间不冒充完成时间。

历史*_TASK、*_REVIEW、SESSION_HANDOFF文件保留作证据，不继续把一切追加到旧日期文件。以后每阶段独立报告，以docs/README.md索引；重要技术决策可按需写docs/decisions/，不要为了形式创建空目录。

首次交付可修正文档中与当前行为冲突的说明，但不要重排整个代码库。尤其注意：手动稿件不再共享自动每日1篇额度，费用不再0.10美元，真实发布已接通但回执自动核实尚有缺口。

停止条件：当前阶段实现、相关测试通过、交付记录完整后即停止，向用户报告。未经新指令不自动启动下一阶段，不追加“顺手”优化。
