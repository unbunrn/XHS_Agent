## 必修 R2：已判过期的直接正文又被末尾补回（P2）

位置：`bot/services/topic_research.py:322`、`:809`。

可信直链初次抓取没有日期，先进入 direct_entry；随后搜索命中相同 URL，补入 2020 年日期，freshness_check 正确判定 stale 并返回 False。但函数末尾只检查列表中是否缺少 direct_entry，又把它插入 entries，最后返回 completed。

离线复现：研究层返回 completed，entries 包含 published_raw=2020-01-01T00:00:00Z；诊断同时含 accepted/date_unknown 与 stale/stale。完整 process_topic_request 会先写入证据，随后被下游的 72 小时时效规则阻塞。这说明下游保护仍然有效，**没有证明会发布过期帖子**，但研究层状态错误、产生不应进入的证据，并造成“研究成功却最终阻塞”的矛盾。

修复要求：直接候选在搜索元数据更新后若失效，清除其后备资格；只有仍通过最终校验的候选可以补回结果。不要用“搜索失败时允许已取得的有效直链”作为恢复已被明确拒绝材料的理由。统一最终标题、日期、正文对应的诊断状态；不要只改一行 return 而保留旧 direct_entry。

验收：

1. 无日期直抓 + 同 URL 明确过期日期：研究结果不含该正文，不返回 completed，完整流程不得写入该正文证据。
2. 同 URL 新鲜日期：正确复用正文，不额外抓取。
3. 无搜索结果：有效直链路径仍可按现有未知日期策略处理，不伪造日期。
4. 被拒绝直链 + 另一条有效候选：仅返回有效候选。

复现脚本：`var/tests/parent_s1_rereview_probe.py`；结果：`var/tests/parent-s1-rereview-probe.log`。脚本中 topic_check 固定通过以隔离日期故障，完整流程另用真实 topic 检查验证了下游会阻塞。
