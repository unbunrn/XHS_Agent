## 唯一必修项：不能把同一托管平台其他组织一起验证

位置：`bot/services/source_identity.py` `_link_relation`。当前检查 HTTP URL 的 exact hostname，却未检查路径中的组织/项目范围。

独立假数据反例：

- 基础可信官网正文：`Our official repository is https://github.com/real-vendor/fable .`
- 待核验正文 URL：`https://github.com/other-owner/fable`
- 假模型输出 role=official、organization=Real Vendor、relation=trusted_link。
- 实际函数结果：`verified=true`、`relation=trusted_link:E1`。

对照：真正链接的 `https://github.com/real-vendor/fable` 同样返回 true。说明程序不能区分官网所指的组织和另一个组织。以上均为构造字符串，未访问 GitHub、未检查任何真实组织。

影响：若模型误认，程序的确定性关系检查无法拦住无关组织，writer 会得到错误的 source_verified。提示词里的 hosting_platform_is_not_an_organization 不是程序约束，不能代替这一检查。这也是上一轮文档明确要求的“平台不同组织不能通过”，不是新增需求。

## 最小修复方案

1. 从实际官网链接保存规范化目标 URL、支持材料 ID 和授权作用域；不能只留下 host 和 trusted_link:E1。
2. 对共享托管站，默认仅接受所链接的具体资源；若支持同项目子页面，必须按明确的平台组织/仓库路径规则限定。不理解路径归属的平台保守保持未核验，不提升整个主机。
3. 自有产品域名的合法站内关系仍可按明确策略支持，但不能因域名或路径前缀碰撞误判。不要用简单 startswith('/real-vendor') 允许 real-vendor-evil；路径按分段边界处理。
4. 官方关系记录、身份缓存与恢复验证使用同一个作用域检查。不能只修首轮，把旧 host 级缓存继续当 verified；策略升级纳入 cache key 或使旧记录失效。
5. 不要改成“所有未知来源一概拒绝”或新增人工域名白名单以绕过 S2 已约定的自动核验目标。
